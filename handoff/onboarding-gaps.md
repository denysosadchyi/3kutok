# Прогалини онбордингу

Це замовлення на хендофф. Новий розробник отримав доступ до репо. Він не був на жодному уроці. Він пройшов репо від `README.md` до коду. Тут записано все, що без усного пояснення лишилось незрозумілим.

Нічого в репо не виправлено. Кожен пункт — питання, яке документація хендоффу має закрити.

## Як читати

- **Питання** — що розробник хоче знати.
- **Що знайдено** — де він шукав і що побачив.
- **Чому незрозуміло** — чого бракує, щоб відповісти без автора.

Номер `G1`, `G2` — ідентифікатор пункту. Документ хендоффу може посилатися на нього.

Пріоритет:

- **[блокує]** — без відповіді розробник не почне роботу;
- **[плутає]** — розробник почне, але з великим ризиком помилки;
- **[дрібне]** — розробник знайде відповідь сам, але витратить час.

## 1. Що це за репо

### G1. Це продукт чи навчальний курс? [блокує]

- **Що знайдено.** `README.md` починає з продукту «Куток». Далі йде розділ «Lesson hub (курс Design Engineering)». `index.html` веде не на продукт, а на урок 1. У корені лежать `concept-lesson.html`, `voice.html`, `ia.html`, `RUN-LOG.md`, `PLAN-lesson6-run.md`, `lesson-2-improvement-plan.md`.
- **Чому незрозуміло.** Репо змішує два продукти: сервіс «Куток» і сайт курсу про нього. Немає списку, які файли належать продукту, а які — курсу. Розробник не знає, що з цього передавати в розробку.
- **Рішення (2026-11-13).** Хендофф передає **продукт** «Куток». Файли курсу в розробку не йдуть. Межу тек — [`README.md`](README.md) → «Що продукт, а що курс».

### G2. Хто замовник і хто власник рішень? [плутає]

- **Що знайдено.** Рішення підписано датами («рішення 2026-10-23»), уроками й кроками («крок 06»). У `lesson-2-improvement-plan.md` згадано «finish review Fable та Astra».
- **Чому незрозуміло.** Немає ролей: хто приймає продуктові рішення, хто — дизайн-рішення. Розробник не знає, до кого йти з питанням.

### G3. Що з цього — правда зараз, а що — історія? [плутає]

- **Що знайдено.** `DESIGN.md` має розділи «Правки уроку 7», «Правки уроку 8», «Правки уроку 9». `tokens.css` у шапці описує міграцію з `ui/kit.css`, якого вже немає. `RUN-LOG.md` описує прогін промптів, а не продукт.
- **Чому незрозуміло.** Чинні правила і журнал змін лежать в одному файлі. Немає позначки «цей розділ — історія, не правило».

## 2. Точка входу і запуск

### G4. Де точка входу продукту? [блокує]

- **Що знайдено.** `index.html` у корені — редирект на `research/research.html` (урок 1). Екрани продукту лежать у `wireframes/`. Окремої стартової сторінки продукту немає.
- **Чому незрозуміло.** Розробник не знає, з якого екрана починається продукт для людини. `_screens.md` починає з «Результати пошуку кімнат», але не каже, що це стартовий екран застосунку.

### G5. Як запустити проєкт локально? [блокує]

- **Що знайдено.** `README.md` каже «статичний сайт без збірки: відкрити `index.html`». У корені є `lan_server.py` і `livereload.py`. `lan_server.py` має жорсткий шлях `/home/hp/from-den/kursy`, якого в новому клоні немає.
- **Чому незрозуміло.** Немає інструкції запуску. Невідомо, чи треба сервер, чи досить відкрити файл. Невідомо, чи працюють екрани через `file://` (вони тягнуть шрифт і іконки з CDN).
- **Рішення (2026-11-13).** Запуск — статичний сервер з кореня репо. Збірки немає. Команди — [`README.md`](README.md) → «Запуск локально».

### G6. Що треба встановити? [плутає]

- **Що знайдено.** Скрипти збірки — Python 3. Версію не вказано. `vendor/package.json` порожній (`{}`), але `vendor/node_modules/` є. Іконки й шрифт беруться з CDN (`iconify-icon@2.1.0`, Google Fonts).
- **Чому незрозуміло.** Немає списку залежностей. Невідомо, навіщо `vendor/` і чи треба `npm install`. Невідомо, чи працює продукт без інтернету.

### G7. Де живий сайт — Vercel чи GitHub Pages? [плутає]

- **Що знайдено.** `README.md` дає два адреси: `https://3kutok.vercel.app` і `https://denysosadchyi.github.io/3kutok/design-system/docs/`. У репо є `.vercel/`.
- **Чому незрозуміло.** Невідомо, що деплоїться куди, як і коли. Невідомо, яка адреса — для замовника, а яка — для команди.

### G8. Які кроки після клонування обов'язкові? [плутає]

- **Що знайдено.** Хук комміту треба вмикати вручну: `git config core.hooksPath .githooks`. Про це сказано в `README.md`, `CLAUDE.md` і в коментарі хука. Хуки Claude Code (`.claude/settings.json`) працюють тільки в Claude Code.
- **Чому незрозуміло.** Немає одного списку «після клонування зробіть 1, 2, 3». Розробник без Claude Code не знає, що частина перевірок у нього не працює.

  - `handoff/README.md` каже «Поки порожньо».
- **Чому незрозуміло.** README тек застаріли. Розробник не може довіряти README теки.
- **Рішення (2026-11-13).** README тек `tokens/`, `concept/`, `wireframes/` і `handoff/` оновлено. Вони кажуть, що в теці зараз і що чинне.

### G10. Що означає кожна тека в корені? [плутає]

- **Що знайдено.** Таблиця в `README.md` описує 9 тек. Не описано: `animations/`, `responsive/`, `assets/`, `vendor/`, `lessons/`, `tools/`, `.impeccable/`, `tokens/`.
- **Чому незрозуміло.** Невідомо, чи `animations/motion-inventory.md` і `responsive/width-audit.md` — чинні рішення чи чернетки. Обидва файли кажуть «на перегляд». Невідомо, чи перегляд був.

### G11. Чому «wireframes» — це готові кольорові екрани? [плутає]

- **Що знайдено.** `wireframes/_conventions.md` каже: «Уся подача ахроматична», «Не визначаємо фірмові кольори». Але екрани в `wireframes/` зібрано з `design-system/index.css`, з коралом, фото й темною темою.
- **Чому незрозуміло.** Назва теки й правила в ній описують ранній етап. Розробник не знає, чи це макет низької деталізації, чи фінальний UI для розробки.
- **Рішення (2026-11-13).** Екрани в `wireframes/` — чинний UI для розробки, зібраний з `design-system/`. Назва теки — історична. Правила ахроматичного етапу в `_conventions.md` позначено як історію.

### G12. Чим `design-system/examples/` відрізняється від `wireframes/`? [плутає]

- **Що знайдено.** `examples/` має `report.html` і `report-sent.html` — екран «Скарга». `design-system/README.md` каже: це перевірка самодостатності системи. У `wireframes/` скарги немає, кнопка ⋯ нікуди не веде (`backlog.md`).
- **Чому незрозуміло.** Невідомо, чи «Скарга» — екран продукту для розробки, чи тільки тест системи. Report і block — частина MVP за `CLAUDE.md`.

### G13. `ui/` чи `design-system/docs/` — де вітрина? [плутає]

- **Що знайдено.** Є дві вітрини: `ui/kit.html` («кожен компонент у кожному стані») і `design-system/docs/` (сторінка на компонент). Є дві сторінки токенів: `ui/tokens.html` і `design-system/docs/tokens.html`.
- **Чому незрозуміло.** Невідомо, яка з них — джерело правди для розробника. Невідомо, чи обидві треба оновлювати й чому.

### G14. Що таке `.impeccable/`? [дрібне]

- **Що знайдено.** Тека є в робочій копії, але `.gitignore` її виключає. `PRODUCT.md` і `DESIGN-artifacts.md` мають позначки `impeccable:*-schema`.
- **Чому незрозуміло.** У новому клоні теки немає. Невідомо, чи вона потрібна для роботи, і що таке impeccable.

## 4. Токени

### G15. Яке джерело токенів справжнє? [блокує]

- **Що знайдено.** Значення кольорів записано в трьох місцях:
  1. `design-system/tokens.css` — два рівні, імена `--grey-50`, `--coral`, `--color-*`.
  2. `concept/tokens.css` — інші імена (`--color-bg`, `--color-accent`), один рівень. Його досі підключає `concept.html`.
  3. Фронтматер `DESIGN.md` — hex з третіми іменами (`paper`, `verified`, `on-coral`).
- **Чому незрозуміло.** `CLAUDE.md` каже, що все живе в одному `tokens.css`. Але дві інші копії є, і їх ніхто не позначив як застарілі. Невідомо, що змінювати, якщо міняється колір.
- **Рішення (2026-11-13).** Чинне те, що в `design-system/`. Єдине джерело токенів — `design-system/tokens.css`. `concept/tokens.css` і hex у фронтматері `DESIGN.md` — історія, їх не міняють.

### G16. Як токени потрапляють у код розробника? [блокує]

- **Що знайдено.** Токени — CSS-змінні. Немає JSON, немає експорту для платформ, немає пакета.
- **Чому незрозуміло.** Стек не обрано (`CLAUDE.md` → «Технічна реалізація»). Невідомо, чи розробник бере `index.css` як є, чи переносить токени у свій стек. Невідомо, хто тоді тримає синхронізацію.

### G17. Що означають позначки в коментарях токенів? [плутає]

- **Що знайдено.** У `tokens.css`: `[D1]`–`[D12]`, `L2–L9`, `[крок 06]`, «було --color-surface». У `_build.py` і `theme.js`: `B9`, `B10`.
- **Чому незрозуміло.** Немає словника позначок. Розробник мусить шукати їх по `tokens-audit.md`, `backlog.md` і `DESIGN.md`.

### G18. Коли primitive стає semantic-роллю? [плутає]

- **Що знайдено.** `CLAUDE.md`: роль з'являється, коли той самий сенс стоїть у 2+ місцях. `tokens.css` має блок «Одиничні» і «вердикти внизу».
- **Чому незрозуміло.** Правило є, але немає прикладу рішення від початку до кінця. Розробник не знає, хто вирішує «сенс той самий» і де це записати.

### G19. Чому геометрія не має semantic-рівня? [дрібне]

- **Що знайдено.** Колір і рух мають ролі. Відступ, радіус і розмір компонент бере з primitive напряму.
- **Чому незрозуміло.** Правило записано, причину — ні. Розробник не знає, що робити, коли треба змінити відступ «усіх карток», а не одне значення `--space-4`.

## 5. Дві теми

### G20. Чому дві теми, і яка з них головна? [блокує]

- **Що знайдено.** `CLAUDE.md`: темна тема — «частина продукту (рішення 2026-10-23)». `tokens.css` каже, що чотири primitive «[крок 06]» з'явились через «стрес-тест темною темою». `DESIGN.md` описує палітру тільки для світлої теми.
- **Чому незрозуміло.** Немає продуктової причини: хто з людей просив темну тему і навіщо. Невідомо, яка тема за замовчуванням. Невідомо, чи тема йде за системним налаштуванням телефону.
- **Рішення (2026-11-13).** Світла тема — за замовчуванням. Темна вмикається лише вибором людини (кнопка-місяць). Системне налаштування телефону тему не міняє. Так уже працює `design-system/theme.js`.

### G21. Як тема працює в продукті з акаунтом? [плутає]

- **Що знайдено.** Вибір теми живе в `localStorage` (ключ `kutok-theme`). Є два скрипти теми: `design-system/theme.js` (продукт) і `assets/scripts/theme.js` (курс). Вони ділять один ключ.
- **Чому незрозуміло.** Невідомо, чи вибір теми треба зберігати в профілі людини. Невідомо, чи кнопка-місяць у шапці кожного екрана — фінальне рішення чи зручність для прототипу.

## 6. Компонент, патерн, разовий блок

### G22. Де межа між компонентом і патерном? [плутає]

- **Що знайдено.** Компонент — CSS-файл у `components/`. Патерн — HTML-фрагмент у `patterns/`, без стилів, з 3+ екранів. Але `patterns/README.md` каже: фрагмент — «зразок композиції, а не джерело для збірки екранів».
- **Чому незрозуміло.** Патерн ніде не вставляють у код. Невідомо, як розробник має його вживати: копіювати HTML, робити шаблон, чи тільки читати.

### G23. Коли блок переїжджає з `screens.css` у `components/`? [дрібне]

- **Що знайдено.** Правило: разовий блок живе в `wireframes/screens.css`, а з другим екраном переїжджає в `components/`.
- **Чому незрозуміло.** Немає способу побачити, скільки екранів уже має блок. `ui/inventory.md` зібрано 2026-10-09 з «16 сторінок», а зараз сторінок 33. Невідомо, чи інвентар оновлюють.

### G24. Чому тільки кнопка має специфікацію? [плутає]

- **Що знайдено.** `design-system/specs/button.yaml` — «джерело правди для `.button`», з порядком зміни spec → CSS → docs → kit → екрани. Інших специфікацій немає.
- **Чому незрозуміло.** Невідомо, чи це правило для всіх компонентів, чи експеримент. Для інших компонентів джерело правди — CSS чи сторінка `docs/`?

### G25. Що в системі JavaScript, і чи це частина компонента? [плутає]

- **Що знайдено.** `components/button.js`, `components/split.js`, `theme.js`. Поведінку шторки (`inert`, фокус, Escape) записано інлайн-скриптом у `wireframes/_build.py`, а не в системі.
- **Чому незрозуміло.** Невідомо, яка поведінка — контракт компонента, а яка — тимчасовий код прототипу. Розробник не знає, що з цього переносити.

## 7. Як додати новий екран

### G26. Які кроки, щоб додати новий екран? [блокує]

- **Що знайдено.** Є окремі правила в різних файлах:
  - `_build.py` — додати виклик `page(...)`;
  - `_screens.md` — рядок у таблиці станів;
  - `sitemap.md` — назва екрана;
  - `_conventions.md` — «новий екран додається одним пунктом» у дереві хабу;
  - дерево хабу в `lessons/index.html` написано вручну.
- **Чому незрозуміло.** Немає одного покрокового рецепта. Невідомо, у якому порядку йти. Невідомо, що з цього — для продукту, а що — тільки для курсу.

### G27. Як влаштовано `_build.py`? [плутає]

- **Що знайдено.** Один файл на 829 рядків. Усі екрани, тестові дані (Ірина, Марина, Оля, кімнати) і розмітка — в одному місці. Функції `page()`, `appbar()`, `split()`, `chat_page()` без опису параметрів.
- **Чому незрозуміло.** Немає опису структури файла. Невідомо, чи можна додати екран в окремий файл. Невідомо, звідки беруться `body_class` і `tab`.

### G28. Звідки беруться дані на екранах? [блокує]

- **Що знайдено.** Імена, ціни, станції, повідомлення записано в `_build.py` як константи. Фото — з `visuals/`.
- **Чому незрозуміло.** Немає моделі даних для розробника. `sitemap.md` → «Сутності» описує сутності для дизайну, але не поля, типи й обов'язковість. Невідомо, які дані реальні, а які — приклад.

### G29. Як відрізнити стан екрана від окремого екрана? [плутає]

- **Що знайдено.** `listing-empty.html` існує, хоча `_screens.md` каже: порожнього стану в оголошення немає. Хаб показує його закресленим. `listing-tatarka.html`, `listing-kpi.html` — не стани, а інші кімнати. `chat-maryna.html`, `chat-olia.html` — інші люди.
- **Чому незрозуміло.** Назва файла не каже, що це: стан, інший запис чи екран. Невідомо, навіщо файл стану, якого немає.

### G30. Як екран має поводитись на планшеті й десктопі? [плутає]

- **Що знайдено.** `CLAUDE.md`: адаптив — наступний крок після мобільної версії. Але `--bp-tablet`, `--bp-desktop` і компонент `split` уже є. `responsive/width-audit.md` — «таблиця рішень на перегляд».
- **Чому незрозуміло.** Невідомо, чи адаптив входить у хендофф зараз. Невідомо, чи рішення з `width-audit.md` прийнято.

## 8. Гейт і перевірки

### G31. Що робити, якщо гейт червоний, а терміново? [плутає]

- **Що знайдено.** `CLAUDE.md`: «Гейт не обходити й не послаблювати». Виняток — рядок у `JS_HOOKS` з поясненням.
- **Чому незрозуміло.** Немає процесу для виняткових випадків. Невідомо, хто дозволяє новий токен або компонент і скільки часу це займає.

### G32. Чому заборонено браузерну автоматизацію? [плутає]

- **Що знайдено.** Хук `_gate.py --guard-browser` блокує Playwright, Puppeteer, headless Chrome. Дозвіл — файл `.claude/allow-browser` на одну команду.
- **Чому незрозуміло.** Причину не записано. Розробник не знає, як тоді перевіряти екрани: тести, скриншоти, регресію. Невідомо, чи заборона діє для CI.

### G33. Чи є тести? [дрібне]

- **Що знайдено.** Є гейт стилів (`_gate.py`) і лінтер тексту (`tools/ste/check.py`). Немає тестів поведінки, доступності чи візуальної регресії. Немає CI.
- **Чому незрозуміло.** Невідомо, що вважати «готово» для екрана, крім зеленого гейта.

## 9. Тексти

### G34. Які тексти пишемо за STE-UA, а які — за tone of voice? [плутає]

- **Що знайдено.** `CLAUDE.md`: службові тексти — STE-UA, тексти інтерфейсу — `voice.md` і `microcopy.md`. Лінтер STE-UA блокує коміт для всіх staged `.md` і `.html`.
- **Чому незрозуміло.** Екрани `wireframes/*.html` — це `.html` з текстом інтерфейсу. Невідомо, як лінтер відрізняє текст інтерфейсу від службового. Невідомо, що робити, якщо лінтер блокує рядок з `microcopy.md`.

### G35. Що головне: `microcopy.md` чи текст у `_build.py`? [плутає]

- **Що знайдено.** Тексти кнопок і станів стоять у `_build.py`. `microcopy.md` має розділи «Розбіжності» і «Звірка після переписування».
- **Чому незрозуміло.** Невідомо, яке джерело перемагає при розбіжності. Невідомо, чи є ключі рядків для локалізації.

## 10. Продукт і межі MVP

### G36. Які екрани MVP ще не намальовано? [блокує]

- **Що знайдено.** У `wireframes/` є 5 екранів: результати пошуку, оголошення, профіль, чат, перелік чатів. `sitemap.md` має більше: наприклад, «Створення / редагування оголошення [S]». MVP за `CLAUDE.md` вимагає верифікацію телефону, report, block, модерацію.
- **Чому незрозуміло.** Немає екранів реєстрації, верифікації номера, власної анкети, створення оголошення, блокування, черги модерації. Невідомо, чи вони в скоупі хендоффу, чи будуть пізніше.

### G37. Як обидві сторони рівноправні, якщо намальовано шлях однієї? [блокує]

- **Що знайдено.** `CLAUDE.md`: обидві сторони публікують анкету й пишуть першими. Усі екрани — шлях Марти, яка шукає кімнату. Шлях Андрія (має кімнату) не намальовано.
- **Чому незрозуміло.** Невідомо, як друга сторона бачить продукт. Невідомо, чи «Результати пошуку кімнат» мають режим «пошук людей».

### G38. Що з позначками `[?]` у вимогах? [плутає]

- **Що знайдено.** `sitemap.md`, `PRODUCT.md`, `CLAUDE.md` мають позначку `[?]` — «непідтверджене». Наприклад: фото в оголошенні, гендерні уподобання, метро чи райони. Інтерв'ю не проводили.
- **Чому незрозуміло.** Невідомо, що розробник має робити з `[?]`: будувати, пропустити чи будувати гнучко. Немає списку рішень, які чекають на ресерч.

### G39. Що таке «Related 1–5», «Main job» і персони? [дрібне]

- **Що знайдено.** Кожен екран у `_build.py` має `job="Related 1 — …"`. Персони Марта й Андрій — синтетичні (`PRODUCT.md`).
- **Чому незрозуміло.** Розробник без уроку 2 не знає, що це jobs з `jtbd.md`. Невідомо, чи це поле потрібне в продукті, чи тільки в прототипі.

### G40. Яка поведінка за межами вигляду? [блокує]

- **Що знайдено.** `flows.md` описує кроки на рівні дизайну. Немає опису: що робить сервер, коли «Надіслати» не спрацювало; як довго живе чернетка; як працює пошук і сортування; що бачить людина, яку заблокували.
- **Чому незрозуміло.** Хендофф має лише вигляд і стани. Логіки, помилок і граничних випадків для розробки немає.

## 11. Борг доступності

Ці пункти знайшло зведення [`a11y.md`](a11y.md) (2026-11-13). Кожен — місце, де уроки 8–11 щось обіцяють, а код чи документація цього не мають повністю. Нічого не виправлено.

### G41. Чому документація не показує фокус скрол-контейнерів і кнопок над фото? [плутає]

- **Що знайдено.** Код має три власні правила кільця фокусу:
  - `.gallery:focus-visible` (`gallery.css`);
  - `.chip-row__track:focus-visible` (`chip-row.css`);
  - `.topbar--over-photo :is(.topbar__back, .topbar__action):focus-visible` (`topbar.css`), біле кільце з ореолом.

  `design-system/docs/_states.py` не показує фокус жодного з них. `gallery` не має ключа в `STATES`, тому `docs/gallery.html` пише «Компонент не інтерактивний — наведення, натискання й фокусу не має». Сторінка «Чип» показує фокус чипа, але не доріжки. `hero-photo` і `topbar` показують кнопки над фото лише під курсором. Клас `.is-focus` у `docs.css` має варіант для `.listing-card__link`, але не для кнопок над фото.
- **Чому це борг.** `DESIGN.md` → «Правки уроку 9» обіцяє: кожен інтерактивний компонент має повний набір станів, блок «5. Стани» показує їх в обох темах. Для цих трьох місць розробник бачить у документації інше, ніж у коді. Біле кільце на фото він знайде лише в CSS.

### G42. Яким має бути кільце фокусу, якщо воно лягає на вміст? [плутає]

- **Що знайдено.** `.gallery` і `.chip-row__track` малюють кільце всередину: `outline-offset: calc(var(--stroke-2) * -1)`. Верхнього поля обидва контейнери не мають (`padding-top` 0).
  - У `.gallery` за CSS верхній край кільця лягає на фото. Правий край на телефоні теж лягає на фото: третя плитка обрізана краєм екрана.
  - У `.chip-row__track` верхній і нижній край кільця лягають на чипи. Вибраний чип має фон `--color-current`. Зелене кільце до нього дає 1.02:1 у світлій темі (`--green` / `--coral-dark`) і 2.21:1 у темній (`--green-light` / `--coral-light`).

  Таблиці контрасту в `tokens.css` мають для `--color-focus` лише пари з фоном сторінки, картки й контролу. Пар «кільце / фото» і «кільце / `--color-current`» немає. Висновок зроблено з CSS. Браузером його не перевіряли, бо гейт блокує браузерну автоматизацію.
- **Чому це борг.** Для кнопок над фото урок 9 уже вирішив цю проблему: «Зелене кільце на фото 3:1 не гарантувало» (`DESIGN.md` → «Аудит кроку 7»). Для скрол-контейнерів такого рішення немає. Розробник не знає, чи вважати кільце, яке частково лежить на фото, прийнятним.

### G43. Хто перевіряє числа в таблицях контрасту? [плутає]

- **Що знайдено.** Контраст пар записано лише коментарями в `design-system/tokens.css`. Жоден скрипт не рахує його для цього файлу. `concept/contrast.py` рахує контраст, але читає `concept/tokens.css` — палітру уроку 6. Гейт (`_gate.py`, функція `contrast_check`) лише попереджає, якщо роль не має жодного рядка з числом. Гейт не рахує співвідношення і не перевіряє, що пара є саме для обох тем. Ручний перерахунок 2026-11-13 (97 рядків) дав два розходження:
  - `--color-text-on-photo / --color-over-photo-dim-hover`, `white / ink-80·white`: записано 9.7, формула дає 9.55;
  - `--color-text / --color-control-active`, `ink / grey-200`: записано 12.6, формула дає 12.66.

  Обидві пари проходять AA. Інших розходжень немає.
- **Чому це борг.** `CLAUDE.md` обіцяє контраст кожної пари в обох темах. Зараз це обіцянка документації, а не перевірка. Якщо хтось змінить hex у PRIMITIVE, таблиця не зміниться і гейт лишиться зеленим. Розробник не знає, чи довіряти числам і як їх перерахувати.
